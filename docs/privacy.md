# 隐私与媒体处理

## 信任边界

前端只负责预览和提交隐私矩形。所有公开发布的媒体必须由 Node.js API/Worker 使用服务端 Sharp 管线生成。客户端上传的“已模糊图片”仍会重新处理，不能直接进入公开桶。

## 处理步骤

1. API 校验用户、文件类型、大小和配额。
2. API 返回短期签名 URL，浏览器将原图上传到私有 `map-quarantine` 桶。
3. `/media/uploads/:id/complete` 校验对象确实存在且大小一致。
4. Worker 从隔离桶读取原图。
5. 如果启用 ClamAV，先执行 `INSTREAM` 恶意文件扫描。
6. Sharp 按 EXIF 方向旋转图片，并在重新编码时移除 EXIF/GPS 等元数据。
7. Worker 合并用户矩形和可选检测器返回的敏感区域。
8. 服务端对区域进行安全边距扩展和模糊。
9. Worker 重新编码 WebP 并生成缩略图、SHA-256 和感知哈希。
10. 没有自动检测器时，处理结果停留在私有桶并标记 `manual_review`。
11. 审核员通过 10 分钟签名 URL查看私有处理结果并确认隐私。
12. 只有确认后，处理图和缩略图才复制到公开桶并标记 `ready`。
13. 原图默认在 24 小时后由维护任务删除；失败媒体最多保留 7 天。

## 对象台账、处理尝试与中断恢复

所有桶对象在写入成功后立即登记 `media_object_ledger`（桶名+对象键唯一），任何时刻残留对象都能被归属到媒体和具体处理尝试：

- `media_processing_attempts` 记录每次首次处理（`initial`）、用户重试（`retry`）和中断恢复（`recovery`），包含触发者、worker、起止时间和错误码。
- 处理产物键带尝试 ID：`processed/<mediaId>/<attemptId>.webp`，重试不覆盖旧产物；成功提交时同一事务切换引用，旧产物转 `superseded` 并物理删除。
- worker 认领任务时对媒体行加锁并写入尝试记录，防止重复任务双重处理；维护任务把超过 20 分钟仍在运行的尝试标记 `lost` 并重新入队，也恢复"已置 processing 但从未被认领"的媒体。
- 处理失败时只清理本次尝试实际写入并已登记的对象；公开桶对象立即删除（隐私优先），隔离桶半成品设短宽限后由维护任务收口。
- 维护任务每轮分页列举两个桶（游标存于 `media_reconcile_cursors`）：与台账互相校验，对处于稳定终态（`manual_review`/`ready`）但引用列丢失的对象**重建引用**；无法归属的私有桶对象登记归属线索并保留 72 小时宽限（`ORPHAN_QUARANTINE_GRACE_HOURS`）供人工追溯，公开桶无台账对象只给 15 分钟（`ORPHAN_PUBLIC_GRACE_MINUTES`）后强制删除。
- 迁移前的旧布局（`processed/<mediaId>.webp`）仍被识别为存量对象处理。
- 台账行物理删除后保留 `deleted` 墓碑，可完整追溯写入、重试、替换与删除历史。

## 数据要求

- 原始文件对象键不可预测，隔离桶不允许匿名读取。
- 公开桶只允许已经过隐私确认的派生图。
- 日志中不得记录原图 URL、访问令牌、密码或完整个人信息。
- 默认不采集用户定位轨迹；浏览器定位必须由用户主动触发。
- 私人住宅内部、受限区域和实时人员位置不属于 V1 允许内容。
- 删除媒体时同时清理隔离原图、服务端处理图和公开派生图；所有删除以对象台账为准，S3 删除失败的对象会进入宽限并由对账任务重试，不会静默残留。
- 台账中的 `deleted` 墓碑与处理尝试历史用于事故追溯，不包含图像内容本身。
